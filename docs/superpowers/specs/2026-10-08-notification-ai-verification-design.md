## 0. 需求溯源（五问）

1. **谁要的**：项目所有者本人。
2. **解决什么已发生的问题**：邮件到达时，验证码和验证链接散落在正文里，用户必须打开邮件、找到内容、再手工复制或打开，容易漏掉。
3. **不做会怎样**：验证码和验证链接仍要手工查找，通知只告诉“有新邮件”，不能直接完成下一步。
4. **怎么算做成**：见第 5 节验收标准 R1–R14；AI 识别成功时，Windows 原生通知直接出现对应按钮，点击后才复制验证码或打开验证链接。
5. **为什么不是只改样式**：要新增 AI 外发例外、识别结果校验、系统通知动作回调和剪贴板处理，涉及安全边界和后台进程行为。

## 1. 目标与边界

### 1.1 本规格包含

- 在设置页「AI功能」里新增「通知智能识别」高级开关，默认关闭。
- 由用户选择该功能使用的 AI 站点和模型；选择方式复用现有功能级模型映射。
- 开关打开并确认风险后，新邮件正文自动发往所选 AI，不再逐封弹授权确认。
- AI 识别验证码和验证链接，识别成功后弹 Windows 原生系统通知。
- 正文里的验证链接以超链接（`<a href>`）形式出现时也要识别：切段取可见文字的同时，另抽 href 一并送检。
- 点击普通新邮件通知的通知体，显示主窗口并定位、打开对应邮件。
- 识别到验证码或验证链接时，通知正文显示发件人名字和验证码 / 链接原文，并带「复制验证码」「打开验证链接」按钮；只有用户点击按钮才执行操作。
- 验证码和验证链接通知固定请求系统「长」档停留；普通新邮件通知保持现有默认行为。
- AI 识别失败、超时或没识别到结果时，退回普通新邮件通知。

### 1.2 本规格不包含

- 不做自绘右下角通知窗口。
- 不做精确到秒的停留时间设置；系统原生通知只能使用「短」「长」等系统档位，最终显示由 Windows 控制。
- 不做附件内容识别；只处理邮件正文文本。
- 不做多个验证码、多个链接的选择界面；第一版只取第一个通过校验的结果。
- 不改变普通翻译、摘要、润色、起草的逐次外发确认规则。
- 不做 macOS / Linux 的原生通知按钮适配；项目当前以 Windows 为发布目标。

## 2. 架构决策（含反选理由）

### Decision D1：高级开关放在「AI功能」，开关本身就是长期外发授权

- **Reason**：用户明确要求打开开关后直接发送新邮件正文给云端 AI，不再逐封确认。
- **Alternatives Considered**：每次通知前再点一次授权；第一版只允许本机模型自动识别。
- **Rejected Because**：用户明确选择“打开后直接发”；逐封授权无法满足该需求。
- **Trade-offs Accepted**：这是对主规格 R10「每次调用前要求授权」的明确例外。风险必须集中在开关开启时解释清楚，开关关闭后立即停止自动外发。

### Decision D2：使用 Windows 原生系统通知，不自绘通知窗口

- **Reason**：用户要求优先原生；`notify-rust` 的 Windows 实现支持按钮和动作回调，能完成复制和打开两个动作。
- **Alternatives Considered**：应用自绘右下角通知。
- **Rejected Because**：自绘虽然能精确控制秒数，但改动更大，且当前用户已接受原生通知的外观和系统时长限制。
- **Trade-offs Accepted**：通知按钮样式、显示位置和最终停留时间由 Windows 决定。

### Decision D3：验证码和验证链接通知固定使用系统「长」档

- **Reason**：用户明确要求这两类通知设置为长。
- **Implementation**：发送时使用不低于 25 秒的超时请求，使 Windows 映射到「长」档。
- **Trade-offs Accepted**：应用不能保证 Windows 在右下角停留的确切秒数；系统设置、专注助手和通知中心行为优先。

### Decision D4：识别成功时，通知正文显示发件人和验证码 / 链接原文

- **Reason**：用户 2026-10-08 明确要求——识别到验证码或链接时，通知里要显示发送方名字，下面直接放验证码或链接，再带按钮。
- **Implementation**：通知标题放发件人名字；正文直接放验证码 / 验证链接原文；按钮仍是「复制验证码」「打开验证链接」。
- **Alternatives Considered**：只在通知里写“识别到验证码 / 验证链接”，不显示原文（v1.0 原方案）。
- **Rejected Because**：用户要一眼看到码或链接，不想再多点一步。
- **Trade-offs Accepted**：验证码和链接原文会进 Windows 通知中心，可能长期驻留、被旁人看到；这是用户明确选择，风险须写清（见第 6 节）。

### Decision D5：AI 输出按不可信内容处理

- **Reason**：邮件正文可能包含提示注入，模型输出也可能被正文诱导。
- **Implementation**：只接受结构化结果；验证码和链接必须重新校验；模型输出不能直接触发复制、打开、发信、写库或执行命令。

### Decision D6：只由用户点击触发动作

- **Reason**：项目安全铁律要求邮件正文不能自行触发跳转或外部动作。
- **Implementation**：通知只缓存校验后的候选值；点击「复制验证码」才写剪贴板，点击「打开验证链接」才调用系统浏览器。

## 3. 接口与数据

### 3.1 设置数据

后端 `AppSettings` 新增字段：

- `notify_ai_enabled: bool`：是否开启通知智能识别，默认 `false`。
- 老配置文件缺这个字段时按 `false` 处理。

前端设置快照同步新增：

- `notifyAiEnabled: boolean`。

该功能使用的 AI 站点和模型不塞进 `settings.json` 的简单字段，而是复用现有 `ai_model_map`：

- 新增功能标识：`notification_verify`。
- 设置页为「通知智能识别」单独选择站点和模型。
- 未选择有效站点或模型时，开关不可开启，并提示先配置 AI 站点。

### 3.2 AI 侧接口

新增一个内部识别入口，供后台通知循环调用：

- 输入：邮件正文纯文本、发件人、主题和邮件编号。
- 输出：经过本地校验后的 `VerificationFinding`：
  - `code: Option<String>`
  - `link: Option<String>`
- 不向前端返回正文、验证码或链接，除非后续单独设计“查看识别结果”。
- 不写正文、验证码、链接到审计或日志；审计最多记录调用功能、站点、模型、是否成功、耗时。

建议模型返回约定：

```json
{
  "code": "123456",
  "link": "https://example.com/verify",
  "confidence": 0.95
}
```

模型返回的任何内容都要本地再校验，不能直接信任 `confidence`。

### 3.3 通知动作标识

- `copy_code`：复制验证码。
- `open_link`：打开验证链接。

动作标识只用于程序内部匹配按钮，不展示给用户。

### 3.4 通知数据

新增内部结构 `VerificationNotification`，包含：

- 邮件编号、账号名、发件人、主题。
- 可选的校验后验证码。
- 可选的校验后验证链接。

验证码和链接只在这个结构及其动作回调闭包内短暂保存；通知关闭或动作完成后释放，不落库、不写日志。

## 4. 行为

### 4.1 设置页行为

- 「AI功能」下新增「高级功能」或「通知智能识别」区域。
- 区域内有开关、站点选择、模型选择、简短风险说明。
- 开关默认关闭。
- 打开开关时弹一次确认，明确写出：
  - 新邮件正文会自动发往所选 AI。
  - 发往哪个站点、使用哪个模型、是否本地。
  - 开启后不再逐封确认。
  - 关闭开关后立即停止自动外发。
- 用户确认后保存开关；取消则保持关闭。
- 关闭开关立即阻止后续通知智能识别，不影响已经进入回调的原生通知按钮。

### 4.2 新邮件处理流程

每轮新邮件扫描后，对每一封新邮件按以下顺序处理：

1. 检查 `notify_new_mail` 和 `notify_ai_enabled` 是否都为真。
2. 检查主窗口当前是否不在前台；前台时保持现有逻辑，不弹通知，也不做这套 AI 识别。
3. 从本地库读取该邮件正文文本；正文为空、读取失败或只有附件时，走普通通知。
4. 将正文纯文本、发件人和主题发送给所选 AI；正文是 HTML 时，除可见文字外还要把 `<a href>` 的地址一并送检，避免「点这里验证」这类链接漏检。远程图片不加载；附件不发送。
5. 等待识别结果，单封最长等待 15 秒；超时、网络失败、模型报错或结果不合法时，走普通通知。
6. 对模型输出做本地校验：
   - 验证码必须是 4 到 12 位数字或字母数字组合，允许一个连字符；不能是 HTML、链接或提示词。
   - 验证链接必须是绝对的 `http://` 或 `https://` 地址；拒绝 `javascript:`、`file:`、`data:` 以及其它协议。
   - 多个候选时只取第一个通过校验的验证码和第一个通过校验的链接。
7. 至少识别到一个有效结果时，弹带按钮的系统通知；两个都没有时，走普通通知。

每批最多处理 3 封新邮件。每封识别任务互相独立，单封失败不能挡住其它邮件。

### 4.3 原生通知内容

普通新邮件（没识别到验证码和验证链接时）保持现状：

- 标题：`{账号名} 收到新邮件`。
- 正文：主题不为空时 `{发件人}：{主题}`；主题为空时 `来自 {发件人}`。

识别到验证码或验证链接时，改用下面的排版：

- 标题：发件人名字（对应 `notify-rust` 的 `summary`）。
- 正文第一行：验证码，写成 `验证码：{验证码}`（对应 `subtitle`）。
- 正文第二行：验证链接，写成 `验证链接：{链接}`（对应 `body`）。
- 只识别到验证码：第一行放验证码，第二行留空。
- 只识别到验证链接：第一行放验证链接，第二行留空。
- 两者都有：第一行验证码、第二行验证链接。
- 按钮：识别到验证码带「复制验证码」；识别到验证链接带「打开验证链接」；两者都有时两个按钮都在。
- 验证码和链接原文直接显示在通知里，这是用户 2026-10-08 明确要求（见 D4）。

### 4.4 按钮点击行为

- 点击「复制验证码」：
  - 重新确认内存中的验证码仍通过格式校验。
  - 写入系统剪贴板。
  - 不打开任何网页，不写数据库。
  - 失败只记通用错误，不输出验证码。
- 点击「打开验证链接」：
  - 重新校验链接协议。
  - 用系统默认浏览器打开。
  - 不经过命令行拼接，不执行邮件正文中的任何命令。
  - 失败只记通用错误，不输出完整链接。
- 点击普通新邮件通知的通知体：把主窗口叫回前台，并在收件箱里定位、打开对应邮件。
- 点击带按钮的验证通知：仍只响应「复制验证码」「打开验证链接」两个按钮；点通知体暂不定位邮件（第一版不变）。

### 4.5 停留时间

- 验证码和验证链接通知请求系统「长」档。
- 普通新邮件通知保持当前默认行为。
- 不新增“精确停留秒数”的设置项；Windows 原生通知不提供这个能力。
- 如果以后要做精确秒数，另开自绘通知规格。

## 5. 验收标准

- **R1**（MUST）设置页「AI功能」出现「通知智能识别」区域，默认关闭。
- **R2**（MUST）没有配置有效 AI 站点或模型时不能开启，并给出中文提示。
- **R3**（MUST）打开开关时出现一次风险确认，写清站点、模型、是否本地以及“不再逐封确认”；确认后才落盘为开启。
- **R4**（MUST）开关关闭时，后台不发送邮件正文给 AI，也不产生验证码 / 验证链接按钮通知。
- **R5**（MUST）开关开启且窗口不在前台时，新邮件正文会自动发往所选 AI；主窗口在前台时不发送。
- **R6**（MUST）识别到验证码时出现原生「复制验证码」按钮；点击前剪贴板不改变，点击后才写入。
- **R7**（MUST）识别到验证链接时出现原生「打开验证链接」按钮；点击前不打开浏览器，点击后才打开。
- **R8**（MUST）验证码和验证链接同时存在时，原生通知同时出现两个按钮。
- **R9**（MUST）验证码和验证链接通知请求系统「长」档停留；普通新邮件通知行为不变。
- **R10**（MUST）AI 超时、失败、没识别到、正文为空时，退回普通新邮件通知。
- **R11**（MUST）识别到验证码或链接时，通知正文显示发件人名字和验证码 / 链接原文，并带对应按钮；验证码和链接不写日志、不写数据库。
- **R12**（MUST）普通翻译、摘要、润色、起草仍保持逐次外发确认，不受本功能影响。
- **R13**（MUST）窗口不在前台时弹出的普通新邮件通知，点击通知体会显示主窗口并定位、打开对应邮件。
- **R14**（MUST）正文里以超链接（`<a href>`）形式出现的验证链接要能被识别；送检前把 href 抽出来一并作为正文送检。

## 6. 安全与隐私

- 本规格经用户 2026-10-08 明确要求，对主规格 R10 设立例外：通知智能识别在开关开启并确认后，可以自动外发新邮件正文，不再逐封授权。
- 例外只作用于通知智能识别，不扩散到其它 AI 功能。
- 开关默认关闭；开启时必须展示外发目标。
- AI 密钥仍只存系统保险箱，不写数据库、不写日志。
- 邮件正文始终是不可信内容；提示注入内容不能改变程序动作。
- AI 输出始终是不可信内容；验证码和链接必须通过本地白名单校验。
- 剪贴板和外部打开只能由用户点击原生通知按钮触发。
- 验证码和链接不落库、不写日志；只在识别成功的通知正文里显示（用户明确要求），普通新邮件通知不含原文。
- 已知风险：显示原文会让验证码 / 链接进入 Windows 通知中心，可能留存在系统里；这是用户明确接受的选择。
- 读取正文时继续遵守远程图片默认拦截，不因为识别需求加载远程资源。
- 失败信息只写通用中文提示，不含正文、验证码、完整链接和密钥。

## 9. 技术核验（2026-10-08 已查依赖源码）

本规格最要紧的两个「到底能不能做」，已直接翻当前锁定的 `notify-rust 4.18.1` 源码确认成立，方案可落地：

1. **Windows 原生通知按钮能做。** `notify-rust` 的 Windows 后端（基于 `tauri-winrt-notification`）已经实现按钮与动作回调：
   - `Notification::action(标识, 文案)` 把一对「标识 + 按钮文案」存进 `actions`；
   - 展示时逐个映射成系统 toast 按钮（`toast.add_button`）；
   - 用户点按钮后经 `on_activated` 回调把该「标识」送回，`NotificationHandle::wait_for_action` / `wait_for_response` 能拿到；
   - 对应本规格要用的两个动作标识 `copy_code` / `open_link`（见 3.3）。
2. **系统「长」档停留可控。** Windows 后端把停留映射成系统两档：
   - `Timeout::Default` → 短档；`Timeout::Never`，或 `Timeout::Milliseconds(t)` 且 `t ≥ 25000` → 长档；
   - 所以验证码 / 验证链接通知用 `Timeout::Never`（或 ≥25 秒）就能请求「长」档，对应 D3 与 4.5。

3. **点击通知体可拿到回调。** `notify-rust` 的 Windows 后端在用户点击通知体时回传 `NotificationResponse::Default`，点按钮时回传 `NotificationResponse::Action(标识)`；所以普通通知点击打开邮件用 `Default`，验证通知的两个按钮用 `Action`（对应 R13、R6、R7）。
实现要点与仍需真机验收的地方：

- 按钮回调必须在通知句柄上单独等待。现在的代码是「`show()` 完就把句柄丢了」，要做按钮就不能这么写，得把句柄留下来等事件——这是 T5 的实现要点。
- 系统「长」档的真实秒数、以及专注助手 / 通知中心会不会吞掉停留，仍由 Windows 决定，应用不能保证，见第 8 节。
